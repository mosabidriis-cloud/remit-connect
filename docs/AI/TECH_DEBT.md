# Technical Debt

Tracks known future technical improvements. Only items already evidenced in the repository or existing docs/AI files are recorded here - nothing is speculative.

## Architecture

- Reporting: the `PERFORMANCE` report category and its report types (`BRANCH_PERFORMANCE`, `OFFICER_PERFORMANCE`, `PROCESSING_TIME`, `RETURN_RATE`, `PROOF_COMPLETION`, `WORKLOAD`) are defined in `types/report.ts` but have no corresponding definitions in `reportService.ts` (only `VOLUME` report definitions exist). REPORTING_STANDARDS.md requires both categories. Sprint 16's architecture review established that this is not simply unwritten work: `OFFICER_PERFORMANCE`, `PROCESSING_TIME` and the speed component of `BRANCH_PERFORMANCE` have no computable data source today (see Correctness, below). Feasibility per report is assessed in REPORTING_ARCHITECTURE.md Section 5. PARTIALLY RESOLVED (Sprint 16 M4.3): `BRANCH_PERFORMANCE` and `PROOF_COMPLETION` now have definitions and generate operations, built only from data that genuinely exists - neither claims a duration metric. `OFFICER_PERFORMANCE`, `PROCESSING_TIME`, `RETURN_RATE` and `WORKLOAD` remain undefined, the first two blocked by D-6.
- RESOLVED (Sprint 16 M4.4): the M4.3 notes about the separate Performance registry and the legacy `createVolumeReportResult` path are both closed - the registries were merged and the entire `location.state` path (`createVolumeReportResult`, `createSharedBatchResult`, `createTransactionResult`, `createBranchBatchResult`, `getVolumeRows`, `getVolumeMetrics`, the row-mapping helpers, and five now-unused types) was deleted.
- **No transaction date is captured on upload** (found during Sprint 16 M4.4 runtime verification; **scheduled for Sprint 17 M4 under DEC-011** - the real export has a `Date` column in `DD/MM/YYYY`, so the data exists). `excelValidationService` sets `transactionDate: ""` on every imported `Beneficiary` - the required-column list does not include a date, and nothing populates it later. Consequence: the Transaction Date column reads "None" in every transaction-level report, and date filters cannot narrow transaction rows at all (an empty date is skipped rather than excluded, so filtering silently has no effect there). Batch-level reports are unaffected - they filter on `SharedBatch.uploadDate`, which is real. Not fixed: adding a date column to the import contract is a business decision about the Direct Remit file format, not an implementation detail.
- **The Reports page uses a hardcoded actor** (Sprint 16 M4.4). `ReportsPage.tsx` declares a fixed `OPERATIONS_MANAGER` `ProjectionScope` because REOS has no current-user context - the same approach `ProofDownloadPage.tsx` already takes. Reports are an Operations Manager capability with enterprise-wide visibility (BUSINESS_RULES.md), so the scope is correct today, and Branch Officer scoping is already enforced by the projection layer for whatever actor it is given. When a real session actor exists, this constant is what it replaces.
- Proof Management and Reporting modules predate the Sprint 10 Enterprise UI reset and are not represented in ROADMAP.md's current sprint numbering. See MODULE_STATUS.md ("Open Item").
- RESOLVED (Sprint 14 Milestone 1 + 1.5): Shared Batch, Branch Assignment, Branch Processing, and Proof Management now share one in-memory store (`sharedBatchStore.ts`) and one canonical Assignment workflow (`branchAssignmentService.ts`). Previously this section noted the missing store and a second, duplicate Assignment-creation path in `SharedBatchUploadPage.tsx`; both are resolved. See DECISIONS.md DEC-006.
- RESOLVED (Sprint 15 M3): `src/features/reos/constants/routes.ts` was unreferenced - nothing imported it, and it duplicated (as string constants) route paths declared in `src/routes/AppRoutes.tsx`. Deleted, same resolution as the Sprint 14 deletion of `ReosRoutes.tsx`.
- `src/features/reos/routes/` is now an empty directory containing only a placeholder `index.ts` (`export {};`), after `ReosRoutes.tsx` was deleted in Sprint 14 stabilization. The stub matches the project's existing barrel convention (`src/features/reos/index.ts` is identical), so it was left in place; remove if the convention is dropped.
- RESOLVED (Sprint 16 M4.1-M4.5): **Reporting and the Operations Dashboard had no data source.** Both `ReportsPage.tsx` and `OperationsDashboardPage.tsx` derived their data from React Router `location.state`, and nothing in `src` navigated to `/reos/reports` or `/reos/dashboard` with state - the Sidebar entries are plain `href`s and `LoginPage` navigates with only `{ replace: true }`. Reached the way a real user reaches them, both rendered permanently empty. Invisible to `tsc` and `npm run build`. Both now consume `reportService`, which reads live operational data through `reportingProjectionService`; each was verified live in a browser across the full workflow. **No REOS page reads operational data from `location.state` any more.**
- RESOLVED (Sprint 16 M4.1, DECISIONS.md DEC-007): Reporting could not enumerate operational data. `sharedBatchStore.ts` exposed only `getSharedBatch(id)`, `getAssignment(id)` and `getAssignmentsByBranch(branchId)`; `branchProcessingQueueService.ts` only the per-branch `getBranchProcessingQueue(branchId)`. Since Operations Manager visibility is enterprise-wide (BUSINESS_RULES.md, frozen), Reporting could not assemble an enterprise-wide result set without knowing every branch id in advance. Resolved by three additive read-only accessors - `getAllSharedBatches`, `getAllAssignments`, `getAllBranchProcessingQueueItems` - each returning `readonly` arrays of deep copies, exposing no internal collection, triggering no hydration, and modifying no lifecycle or processing state. No existing function's behavior or signature changed.
- RESOLVED (Sprint 16 M4.4): `ReportSourceData.processingBatches` was typed `BranchProcessingBatch[]`, a shape the live processing path never built - it produces `BranchProcessingQueueItem[]`. The projection layer now bridges the two, and `ReportSourceData` itself was deleted along with the rest of the `location.state` machinery.
- **The two report-definition registries were merged** (Sprint 16 M4.4), resolving the M4.3 note about Performance definitions being held outside `getDefinitions()`. Safe now that `ReportsPage` uses the async path rather than the throwing `createVolumeReportResult`, which was deleted.
- `BranchAssignmentPage.tsx` has no way to select a real, previously-uploaded Shared Batch with real beneficiary data - it only ever operates on a self-constructed `SharedBatch` built from manually-typed form values (`createUnassignedSharedBatch`), so any Assignment it creates has zero real transactions (`beneficiaries: []`) and will not populate Branch Processing's queue. Only `SharedBatchUploadPage.tsx`'s flow (which has real uploaded beneficiary data) produces Assignments with actual transactions. Discovered during Sprint 14 Milestone 1.5 consolidation; not resolved because giving `BranchAssignmentPage.tsx` access to real uploaded batches would be a redesign of how it sources data, out of that milestone's scope.

## Audit (newly recorded, Sprint 16 architecture review)

REOS constructs audit records and persists none of them. BUSINESS_RULES.md states "All business actions must be auditable" and "Audit logs are immutable", so this is a gap against an existing business rule, not a missing nice-to-have. It blocks the entire Audit report category (Assignment History, Lifecycle History, Processing History, Proof Download History, User Activity).

- `TransactionProcessingAudit` is built by `transactionProcessingService`'s `addProofToTransaction` / `completeTransaction` / `returnTransaction`, returned to the caller, and stored nowhere. Compounding this, the live processing path is `branchProcessingQueueService`, which never calls those functions and produces no audit record at all.
- `ProofDownloadHistoryEntry` is returned by `downloadProofZip`, `downloadIndividualProof` and `markBatchDownloaded`, and is held only in component state - discarded on unmount.
- `SharedBatchReassignmentAudit` is returned inside `SharedBatchAssignmentResult` and is not stored.
- `sharedBatchStore.updateSharedBatchLifecycleStatus` overwrites `lifecycleStatus` in place with no transition log, so lifecycle history is unrecoverable by construction. `SharedBatch` retains only `lastReassignedByUserId` / `lastReassignedAt` / `lastReassignmentReason` - the most recent event, not a history.

Not fixed: an append-only audit trail is state that must outlive the actions it records, which is governed by DEC-004 and ARCHITECTURE.md's persistence boundary. Escalated as REPORTING_ARCHITECTURE.md Decision D-5. Recommendation recorded there: build the audit trail as its own scoped work first, and do not implement Audit reports against absent data.

## Shared Batch Import (Sprint 17)

Found by analysing a real production Direct Remit export on 2026-08-02 and running it through the shipped `excelValidationService`. Before Sprint 17 it produced **0 valid records from 63 real transactions**, 75 ERROR issues, `readyForAssignment: false`.

- RESOLVED (Sprint 17 M1): the service assumed the header was the sheet's first row, so a real export - which places the header on row 2 beneath a blank row - had every required column reported missing before any row was read. It also treated the headers a paginated export repeats mid-sheet (rows 35, 71) as transactions. Both fixed by locating the header and skipping repeats; issues now cite true spreadsheet row numbers instead of numbers derived from a filtered array index, which drifted whenever any row was skipped.
- RESOLVED (Sprint 17 M2, DEC-013): `TOTAL` subtotal rows were imported as transactions. The real file carries three, one per page section; they are neither blank nor headers, so M1's scope did not cover them and they survived as phantom invalid records. Fixed by structural detection - a row is a transaction only if it carries a transaction identifier - rather than by matching the display text "TOTAL", which may be localised.
- RESOLVED (Sprint 17 M2): the column contract did not match the source system, and amounts were unparseable. Required fields now resolve through an alias table (`Payout Ref. No` -> `Direct Remit Reference`, `Receiver Name` -> `Beneficiary Name`, `FC Amount` -> `Amount`, `CCY` -> `Currency`), and amount parsing tolerates padding, non-breaking spaces and thousands separators - all 63 real rows now parse, and the parsed total matches the file's own subtotals to source rounding. `Bank Name` and `Account Number` deliberately have no alias; they arrive as one composite `Bank` column that only M3's shared `parseBankField` may split (DEC-012).
- **A row missing only its transaction identifier is now skipped rather than flagged** (Sprint 17 M2, accepted consequence of DEC-013). This is correct for subtotal rows, which is what the rule exists for. But a genuinely malformed transaction that lost its reference now disappears from the import instead of being reported as invalid, which sits in slight tension with DEC-009's "flag invalid rows for review". Not addressed because DEC-013 specifies skipping; revisit if operators report missing transactions.
- **The file contains two row layouts** (M3). 37 rows carry `Bank = "BANK OF KHARTOUM (Acc No: 4734114)"` with `Dest Country = "Sudan"`; the other 26 carry the bank name in the `Dest Country` column and a bare account number in `Bank`. Account numbers are 7 or 16 digits.
- **`parseBankField` does not implement the frozen rule against real data** (M3, DEC-012). BUSINESS_RULES.md freezes "Bank field is parsed into bankName and accountNumber", but the only implementation lives on the unused CSV path in `sharedBatchService.ts`, and tested against the real file it returns an empty account number for **all 63 rows** because it does not recognise the `(Acc No: ...)` form. The live path meanwhile demands two separate columns, contradicting the frozen rule outright.
- **Bank names are unnormalized across scripts and spellings** - `BANK OF KHARTOUM`, `Bank of Khartoum`, `ALKHARTOUM`, `KHARTOUM BANK`, `khartoum`, `بنك الخرطوم`, `الخرطوم`, plus the typo `BANK OF KHATOUM`. Deliberately **not** addressed in Sprint 17 (DEC-010): deciding two spellings are the same bank is an operations judgement with routing consequences.

## Correctness

- **Branch Processing records no timestamps and no actor attribution** (found Sprint 16 architecture review). `BranchProcessingQueueItem` carries `status`, `proofs`, `returnReason` and `returnComment` but no `startedAt`, `completedAt` or `completedByUserId`. `CreditToAccountTransaction` does define those fields, but the live path never populates them: `proofDownloadService.buildProofDownloadBatchFromSharedBatch` hardcodes `completedByUserId: null, completedAt: null` when mapping queue items. Two consequences: (1) every duration-based and officer-attributed report metric is uncomputable - Processing Time, Processing Throughput, branch processing speed, time-on-hold, Officer Performance, and the User/Officer filter; (2) `dashboardService.getAverageProcessingMinutes` reads `transaction.completedAt`, so "Average Processing Time" resolves to "No data" in the live path and `BranchPerformanceRow.processingSpeedMinutes` is always `null`, which drives `getBranchHealth` to return YELLOW for every branch regardless of actual performance. Not fixed: adding these fields is a Branch Processing change that overlaps that module's already-open actor-role gating decision above. Escalated as REPORTING_ARCHITECTURE.md Decision D-6.
- **`SharedBatch.completedBeneficiaries` and `returnedBeneficiaries` are never incremented** (found Sprint 16 M4.2). Both are set to `0` at every creation site (`sharedBatchService.createSharedBatch`, `excelValidationService`, `BranchAssignmentPage`) and nothing anywhere increments them - Branch Processing tracks completion on its own queue items instead. Consequence: they read `0` even for a fully processed batch, and `reportService.mapSharedBatchToRow` maps them straight into the Shared Batches volume report's `completedCount` / `returnedCount` columns, so that report would show zero completed and zero returned work for a batch that was genuinely completed. `dashboardService` also filters on `returnedBeneficiaries > 0` to build its "Returned Batches" work-queue category, which can therefore never match. Not fixed - keeping these counters in step with the queue is a business-logic change in Shared Batch and Branch Processing, outside M4.2's read-only scope. The projection layer works around it correctly without hiding it: `BatchReportProjection` projects both the stale `SharedBatch` counters and the live queue-derived counts from `getBatchDownloadSummary`, under names that distinguish them.
- **Two transaction status vocabularies exist and one collapses the other** (found Sprint 16 architecture review). `BranchProcessingQueueStatus` is `ASSIGNED | IN_PROGRESS | COMPLETED | ON_HOLD | RETURNED`; `CreditToAccountTransactionStatus` is `PENDING | COMPLETED | RETURNED`. `proofDownloadService.toTransactionStatus` maps `ASSIGNED`, `IN_PROGRESS` and `ON_HOLD` all to `PENDING`, destroying the on-hold distinction. Any "Pending Work" or "On Hold Transactions" report must therefore project from `BranchProcessingQueueItem` directly. Recorded as a design constraint, not to be resolved by introducing a third status enum.
- RESOLVED (Sprint 15 M1.75): `branchProcessingQueueService.hydrateBranchProcessingQueue` was not idempotent - it ran on every mount of `BranchProcessingQueue.tsx` and unconditionally rebuilt that branch's queue from scratch (fresh `ASSIGNED` status, empty `proofs`, branch-level status reset to `PROCESSING`), silently discarding real completed work whenever a user navigated away and back. Pre-dated Sprint 14/15 (Sprint 13 code). Fixed by preserving existing queue items by their deterministic id and no longer resetting branch-level status on rehydration; only genuinely new assignment-beneficiary pairs get fresh items. Verified live against the exact reproduction that found it - see CURRENT_SPRINT.md, "M1.75".
- `proofOfPaymentService.markProofDownloaded` (sets an individual `ProofOfPayment.status` to `DOWNLOADED`) is never called anywhere, including by `downloadIndividualProof`/`downloadProofZip`. Wiring it in needs a write path back into `branchProcessingQueueService`'s queue-item state and an unstated product decision: does a ZIP download mark every included proof downloaded, or only individually-downloaded ones? Left as an open business decision, not assumed.
- Proof expiry is only enforced via the `status` field, never against `expiresAt`. Nothing automatically flags an expired proof as `EXPIRED` (no scheduler - BUSINESS_RULES.md puts one out of scope), so a proof past its 90-minute window but never explicitly marked can still appear downloadable.

## Linting (newly surfaced, Sprint 15 Stabilization & Closure)

`npm run lint` had not been run as part of this documentation-driven workflow before Sprint 15 Stabilization & Closure. Running it surfaced pre-existing issues, all in files Sprint 15 did not modify (verified against `git status` - none of these files appear in this session's changes):

- `BranchProcessingQueue.tsx`: three `react-hooks/set-state-in-render` errors - `setQueueItems`/`setSelectedItemId`/`setBranchStatus` are called synchronously inside a `useMemo`, which the current ESLint React Hooks rules flag as a potential infinite-loop risk. Pre-dates Sprint 14/15.
- `ProofDownloadPage.tsx`: one `react-hooks/set-state-in-effect` error - `setBatch` is called synchronously inside the Sprint 14 Milestone 2C auto-transition `useEffect`. Pre-dates Sprint 15.
- `layout/Sidebar.tsx`: two `react-refresh/only-export-components` errors, pre-existing, Enterprise UI shell (Sprint 10).
- `excelValidationService.ts`: two unused-variable errors, pre-existing (Sprint 11).
- Three further errors/warnings in `funding/`, `authService.ts`, `fundingRequestService.ts` - entirely unrelated modules, out of REOS and out of scope.

Not fixed - none are dead code, none were introduced by Sprint 15, and fixing the two React Hooks findings above in files Sprint 15 didn't otherwise touch would exceed this sprint's approved scope. Recommend a follow-up sprint audit `npm run lint` cleanly, particularly the two `set-state-in-*` findings since they sit in files this and the preceding sprint depend on.
