### DEC-008 - The real Direct Remit Excel export is the supported import contract

Persistence is approved for a new, durable **Import Intelligence ledger** - `import_batches` and `beneficiaries` tables in the already-provisioned Supabase project (`remit-connect`, id `czswszihkthyicoifbtx`, connected via the existing `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` and `src/lib/supabase.ts`, previously used only for the Supabase Auth wiring in `authService.ts`). Wiring real authentication is explicitly out of scope (BUSINESS_RULES.md: "Authentication changes" requires explicit approval, not given here) - so the new tables' RLS policies are permissive to the `anon` role, matching REOS's current, already-accepted no-real-session security posture (the same "no actor-role gating" gap already recorded for Branch Processing and Liquidity Management in TECH_DEBT.md) rather than silently fixing it as a side effect.
- Status: APPROVED

### DEC-013 - Transaction rows are identified structurally, by transaction identifier

- Date: Approved 2026-08-02 (Sprint 17 Milestone 2)
- Decision: A row is a transaction row if and only if it carries a transaction identifier (Direct Remit Reference / Payout Ref. No). Rows without one are not transactions and are skipped, including subtotal rows. Detection must not rely on display text. Required columns are resolved through an alias table, so the legacy format and the Direct Remit export share one import path.
- Context: The approved export is a paginated report. It interleaves blank spacer rows, repeats its header at each page break, and writes a `TOTAL` subtotal row per page section. Sprint 17 M1 removed the blank rows and repeated headers, but the three subtotal rows survived as phantom invalid records - visible to the operator under DEC-009 as bogus rows needing review on every import.
- Rationale: The presence of a reference is a structural property of a transaction; the word "TOTAL" is presentation text that may be localised or restyled at any time, and this export is already bilingual. Alias-based column resolution avoids a second parser or a per-format branch, keeping one code path for both contracts.
- Consequence, accepted: a row that carries data but no reference is now skipped silently rather than flagged invalid. That is correct for subtotal rows; for a genuinely malformed transaction missing only its reference it means the row disappears rather than being reported. Recorded in TECH_DEBT.md.
- Status: APPROVED

### DEC-019 - Operational Persistence Milestone 1: Shared Batch/Beneficiary/Assignment persisted; Assignment's transaction lists are a view, not stored data

- Date: Approved 2026-08-09
- Decision: `sharedBatchStore.ts` (`SharedBatch`, `Beneficiary`, `Assignment`) is migrated from an in-memory `Map` to Supabase-backed tables (`shared_batches`, `beneficiaries`, `assignments`), with every exported function keeping its exact name and now returning a `Promise`. `Assignment.assignedTransactions`/`manualReviewTransactions`/`invalidTransactions` are explicitly **not** given their own storage - they are reconstructed at read time by querying `beneficiaries` for the assignment's `shared_batch_id`, filtered by `processing_status_id`, exactly reproducing what `assignmentService.createAssignment` already computed from the in-memory array.

Verified safe by inspection: `Beneficiary.processingStatusId` is set exactly once, at validation time, and never mutated anywhere in the codebase, so a live filter over `beneficiaries` can never drift from a stored copy that doesn't exist.
- Rationale (RLS/branch scoping): a second `SECURITY DEFINER` helper, `current_user_branch_id()`, scopes a Branch Officer's reads to their own branch's `shared_batches`/`beneficiaries`/`assignments` (via `assigned_branch_id`), matching BUSINESS_RULES.md's "Can only view Shared Batches assigned to their branch" - the same pattern `current_user_role()` established in DEC-018, applied a second time rather than inventing a different scoping mechanism.
- Status: APPROVED. Implemented per OPERATIONAL_PERSISTENCE.md Section "Milestone 1." Verified live across two separate browser contexts (9/9 assertions, zero console errors) - the second context, with nothing uploaded in it, showed the real assigned transaction, the definitive proof of persistence. Branch Processing/Liquidity Management/Proof Management remain in-memory, unaffected - later, separately-scoped Phase 2 milestones.

### DEC-020 - Operational Persistence Milestone 2: Branch Processing Queue and Proof Storage persisted together; TransactionProcessingPage.tsx deleted as confirmed dead code

- Date: Approved 2026-08-09
- Decision: `branchProcessingQueueService.ts` (queue-item state and branch-level PROCESSING/COMPLETED lock) and proof-of-payment files are migrated together, in one milestone, to Supabase-backed tables (`branch_processing_queue_items`, `proofs`, `branch_processing_status`) plus a private Supabase Storage bucket (`proof-of-payment`). `TransactionProcessingPage.tsx` and its exclusively-used dependents (`TransactionCard.tsx`, `ProcessingProgress.tsx`, several now-orphaned `transactionProcessingService.ts` functions and `types/transactionProcessing.ts` types) are deleted, confirmed unreachable dead code carrying a parallel, un-migrated implementation of the same workflow.
- Context: OPERATIONAL_PERSISTENCE.md's own "one store, one migration" guiding rule (established in Milestone 1) would normally require two separate milestones here. This decision records the deliberate exception and why.
- Rationale (combining the two migrations): queue-item state and its embedded `proofs` array are facets of one entity (a `BranchProcessingQueueItem`), not independent domains the way Shared Batch and Liquidity are. Splitting them would produce a real, user-visible bad state - a transaction shown as COMPLETED with its proof missing after reload - which violates "no shortcuts, no placeholders" more directly than combining two migrations violates the one-migration guideline.
- Rationale (`addProofToBranchProcessingQueueItem` signature change): the prior signature took an already-built `ProofOfPayment` object generated via `URL.createObjectURL(file)`. A real Storage upload needs the file's actual bytes, which that shape cannot carry - `preserve interfaces wherever possible` gives way here to a genuine external constraint, not an redesign of choice. The new signature `(itemId, file, uploadedByUserId)` is the minimal change that makes real upload possible; `proofOfPaymentService.uploadProofOfPayment` owns the upload and metadata construction, keeping "one owner per workflow" intact.
- Rationale (deleting `TransactionProcessingPage.tsx`): confirmed dead by tracing every `navigate()` call into its route pattern - all of them were self-referential, from within the page itself; nothing else in the app ever linked to it. It implemented proof upload and transaction completion a second time, against a different in-memory model (`CreditToAccountTransaction`, driven by React Router `location.state`, the pattern Sprint 16 eliminated everywhere else). Making it work with real Storage would have meant building the same integration twice - a direct violation of "avoid duplicate services/business logic/parallel implementations." Deleting confirmed-dead code that a live migration would otherwise have to duplicate is a legitimate part of this milestone's scope, not an unrelated cleanup pass.
- Rationale (`branch_processing_status` as its own table): the branch-level PROCESSING/COMPLETED lock is not derivable from queue items alone (a branch with every item terminal is merely *eligible* to finalize, not automatically locked - `finalizeBranchProcessing` is a distinct write) and was not in the original schema draft; added when this was traced through during implementation.
- Status: APPROVED. Implemented per OPERATIONAL_PERSISTENCE.md Section "Milestone 2." Verified live: one continuous session (Operations Manager funds a payout account and assigns a batch; a Branch Officer starts, uploads a real proof image, and completes the transaction, then finalizes the branch), followed by two independent fresh-session checks - a Direct Remit Officer opening Proof Download and successfully loading the uploaded proof via a Storage signed URL, and a brand-new Branch Officer session (zero uploads in that context) showing the same transaction as COMPLETED at 100% with the branch locked. 16/16 assertions passed, zero console errors. Liquidity Management remains in-memory, unaffected - Milestone 3.

### DEC-021 - Operational Persistence Milestone 3: Liquidity Management persisted, closing Phase 2

- Date: Approved 2026-08-13
- Decision: `liquidityStore.ts` (`PayoutAccount`, `FundingEvent`) is migrated from an in-memory `Map` to Supabase-backed tables (`payout_accounts`, `funding_events`, `funding_entries`). Every exported function keeps its exact name and becomes `async`; `liquidityService.ts`'s business logic (validation rules, error messages, the sequential per-entry processing in `recordFunding`) is otherwise unchanged. This is the last Phase 2 milestone - every live REOS operational store is now Supabase-backed.
- Context: OPERATIONAL_PERSISTENCE.md's Upcoming/Roadmap items named this as Milestone 3, the final remaining store after Milestone 1 (Shared Batch/Beneficiary/Assignment) and Milestone 2 (Branch Processing Queue/Proofs). `PayoutAccount.currentBalance` resetting on reload was already recorded (TECH_DEBT.md, 2026-08-08) as the strongest single argument for approving persistence for the remaining stores, since unlike reconstructable operational state, a manually-entered, manually-adjusted balance has no other source of truth to rebuild from.
- Rationale (`payout_accounts` INSERT policy grants Branch Officer, not just Operations Manager): `savePayoutAccount` - the one function every business-logic write funnels through, preserving its interface - always issues a Postgres upsert (`INSERT ... ON CONFLICT DO UPDATE`). Postgres requires the INSERT policy to pass for an upsert even when the row already exists and the statement resolves as an update, so `deductForTransaction` (a genuine, necessary Branch Officer write path, called during transaction completion) could not function under an Operations-Manager-only INSERT policy. Widening it to Branch Officer (scoped to their own branch) accepts the same broad, route-trusted grain already used for `branch_processing_queue_items` in Milestone 2, rather than splitting `savePayoutAccount` into insert-only/update-only paths to preserve a narrower policy - judged not worth the interface change for a single-tenant internal app.
- Rationale (`refreshSignal` passed as an explicit prop, not just used to force a parent re-render): `PayoutAccountManager.tsx` and `FundingRecorder.tsx` previously read `liquidityService` synchronously during render, so any parent re-render (triggered by a shared counter, bumped by either sibling after a write) picked up fresh data from the shared in-memory store automatically. An `async` read cannot happen during render, so the counter is now passed down and included in each sibling's data-fetching `useEffect` dependency array - preserving the original design's actual intent (both children observably back in sync after either writes), not just its mechanism.
- Status: APPROVED. Implemented per OPERATIONAL_PERSISTENCE.md Section "Milestone 3." Verified live across three sessions: one continuous Operations Manager session created and funded a payout account, confirmed via a hard page reload; a brand-new Branch Officer session (zero prior interaction) saw that same account and used it to complete a real transaction; a brand-new Operations Manager session (zero prior interaction) showed the deducted balance - the definitive persistence proof, for both the funding write path and the deduction write path. 8/8 assertions passed, zero console errors. **REOS v1.0 Production Readiness Phase 2 is now complete** - no operational store remains in-memory-only.

### DEC-022 - Production Readiness Phase 3: a real, persisted audit trail closes D-5

- Date: Approved 2026-08-13
- Decision: A new `audit_events` table records every real business action across REOS - Shared Batch upload/confirm/assign/reassign, Branch Processing start/hold/resume/proof-upload/complete/return/finalize, proof download/mark-downloaded, Liquidity account create/update/status-change/funding, and user create/update - via one shared `auditService.recordAuditEvent`, called directly from the service function that performs each action. One unified `AuditEvent` vocabulary replaces the three previously-separate, previously-discarded shapes (`TransactionProcessingAudit`, `ProofDownloadHistoryEntry`, `SharedBatchReassignmentAudit`).
- Context: REPORTING_ARCHITECTURE.md Section 5.3 found the entire Audit report category blocked because "REOS creates audit records but stores none of them," escalated as D-5 and explicitly deferred pending a persistence decision (DEC-004). Phase 2's completion (DEC-019/020/021) removed that blocker - REOS now has real, RLS-backed persistence everywhere an audit write needs to land.
- Rationale (actor role resolved server-side, not client-supplied): every audited action is performed by the currently-authenticated session, so `recordAuditEvent` reads the acting role via the `current_user_role()` `SECURITY DEFINER` RPC (the same helper RLS already trusts, DEC-018) rather than accepting it as an input - a client cannot misreport its own role in its own audit record.
- Rationale (non-blocking writes): a failed audit insert never blocks or throws inside the business action it describes - the same precedent Import Intelligence established (DEC-016): a Supabase outage must degrade to a logged warning, never stop a Branch Officer from completing a transaction.
- Rationale (RLS visibility default): SELECT is restricted to Operations Manager only, matching REPORTING_ARCHITECTURE.md Section 8.1's own stated default for Audit reports ("should default to Operations Manager only") rather than inventing a new visibility rule.

### DEC-024 - Strict RLS enforcement approved for `payout_accounts`

- Date: Approved 2026-08-15
- Decision: The `payout_accounts` table's Row-Level Security must be tightened to strict enforcement, closing the gap DEC-021 accepted provisionally and ARCHITECTURE_HANDOVER.md Section 5 flagged as needing written sign-off: the current INSERT policy is broader than the UI's own intent, and, via Postgres upsert mechanics, allows a Branch Officer to create a payout account for their own branch - an action the UI restricts to Operations Manager only.
- Context: DEC-021 widened `payout_accounts` INSERT to Branch Officer (scoped to their own branch) because `savePayoutAccount`'s upsert requires the INSERT policy to pass even on an update-only call, and accepted the resulting broader grant as "low-risk for a single-tenant internal app" pending sign-off from whoever owns security decisions. That sign-off is given here, in the opposite direction: the broader grant is not accepted as final, and strict enforcement is approved instead.
- Rationale: A payout account is real operational capacity data (DEC-015) with a real, non-reconstructable balance; account *creation* is a supervisory action under BUSINESS_RULES.md's role boundaries (Operations Manager "manages... master data"), not a Branch Officer action, and the current policy permits it only as a side effect of upsert semantics, not by design.
- Status: APPROVED. **Not yet implemented** - this entry records approval to tighten enforcement; the actual policy change (splitting `savePayoutAccount`'s upsert into an Operations-Manager-only insert path and a Branch-Officer-scoped update path, or an equivalent mechanism) is separate follow-up implementation and migration work, to be verified live the same way every other RLS change in this log has been (a real negative-path check, not code review alone).
