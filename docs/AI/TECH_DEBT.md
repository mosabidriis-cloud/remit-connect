Tracks known future technical improvements. Only items already evidenced in the repository or existing docs/AI files are recorded here - nothing is speculative.

## Audit Trail (new module, out-of-sprint, 2026-08-13)

Canonical spec: AUDIT_TRAIL.md. Items recorded there, tracked here for visibility:

- **`USER_CREATED` audit events have been observed to intermittently not persist**, despite `createUser()` completing successfully and `recordAuditEvent` reporting no error. If an operator confirms the upload before that promise resolves, Import Intelligence silently records nothing for that import - a gap that predates Phase 3 and was only noticed because the first placement of the `BATCH_CONFIRMED` audit call shared the same guard (since fixed for the audit call specifically, by giving it its own narrower guard - see AUDIT_TRAIL.md Section 6). ## Shared Batch Import (Sprint 17)

Found by analysing a real production Direct Remit export on 2026-08-02 and running it through the shipped `excelValidationService`. Before Sprint 17 it produced **0 valid records from 63 real transactions**, 75 ERROR issues, `readyForAssignment: false`. As of Sprint 17 M3, the same file produces **63 valid records, 0 errors, `readyForAssignment: true`** - the items below marked RESOLVED are what closed that gap; the remaining items are open and do not block import.

- RESOLVED (Sprint 17 M1): the service assumed the header was the sheet's first row, so a real export - which places the header on row 2 beneath a blank row - had every required column reported missing before any row was read. It also treated the headers a paginated export repeats mid-sheet (rows 35, 71) as transactions. Both fixed by locating the header and skipping repeats; issues now cite true spreadsheet row numbers instead of numbers derived from a filtered array index, which drifted whenever any row was skipped.
- RESOLVED (Sprint 17 M2, DEC-013): `TOTAL` subtotal rows were imported as transactions. The real file carries three, one per page section; they are neither blank nor headers, so M1's scope did not cover them and they survived as phantom invalid records. Fixed by structural detection - a row is a transaction only if it carries a transaction identifier - rather than by matching the display text "TOTAL", which may be localised.
- RESOLVED (Sprint 17 M2): the column contract did not match the source system, and amounts were unparseable. Required fields now resolve through an alias table (`Payout Ref. No` -> `Direct Remit Reference`, `Receiver Name` -> `Beneficiary Name`, `FC Amount` -> `Amount`, `CCY` -> `Currency`), and amount parsing tolerates padding, non-breaking spaces and thousands separators - all 63 real rows now parse, and the parsed total matches the file's own subtotals to source rounding.
- RESOLVED (Sprint 17 M3, DEC-012): `parseBankField` did not implement the frozen rule against real data. BUSINESS_RULES.md freezes "Bank field is parsed into bankName and accountNumber", but the only implementation lived on the unused CSV path in `sharedBatchService.ts` and did not recognise the `(Acc No: ...)` form (empty account number on all 63 real rows), while the live `excelValidationService` path instead demanded two separate columns, contradicting the frozen rule outright. Fixed by extending the one shared parser to three input shapes (labelled account, bare account number with a caller-supplied fallback name, trailing account token) and calling it from `excelValidationService` instead of requiring pre-split columns. There is now exactly one `parseBankField`, used by every import path.
- RESOLVED (Sprint 17 M3): the file's two row layouts - 37 rows carrying `Bank = "BANK OF KHARTOUM (Acc No: 4734114)"` with `Dest Country = "Sudan"`; the other 26 carrying the bank name in `Dest Country` and a bare account number in `Bank` - are both handled by the same `parseBankField` call, with `Dest Country` supplied as the fallback bank name. Verified against real rows from both layouts (Layout B example: `bankName: "بنك الخرطوم"`, `accountNumber: "3686824"`, Arabic script preserved). Account numbers observed at 7 or 16 digits, both handled - the parser does not constrain length.
- **A row missing only its transaction identifier is now skipped rather than flagged** (Sprint 17 M2, accepted consequence of DEC-013). This is correct for subtotal rows, which is what the rule exists for. But a genuinely malformed transaction that lost its reference now disappears from the import instead of being reported as invalid, which sits in slight tension with DEC-009's "flag invalid rows for review". Not addressed because DEC-013 specifies skipping; revisit if operators report missing transactions.
- **Bank names are unnormalized across scripts and spellings** - `BANK OF KHARTOUM`, `Bank of Khartoum`, `ALKHARTOUM`, `KHARTOUM BANK`, `khartoum`, `khartoum bank`, `BANK Of KHARTOUM`, `بنك الخرطوم`, `الخرطوم`, plus the typo `BANK OF KHATOUM` - confirmed still distinct and unmodified after M3's parsing changes. Deliberately **not** addressed in Sprint 17 (DEC-010): deciding two spellings are the same bank is an operations judgement with routing consequences.
- RESOLVED (Sprint 17 M4, DEC-011, 2026-08-05): the real export's `Date` column (`DD/MM/YYYY`) is now mapped to `Beneficiary.transactionDate`, converted to ISO. Not required for row validity - an absent or unparseable date still leaves `transactionDate: ""`, same as before. See CURRENT_SPRINT.md.

## Operational Persistence Milestone 2 (Branch Processing Queue and Proof Storage, out-of-sprint, 2026-08-09)

Canonical spec: OPERATIONAL_PERSISTENCE.md. Items recorded there, tracked here for visibility:

- **`branch_processing_status` is a one-way lock with no reset path** - once a branch finalizes to `COMPLETED`, nothing ever writes it back to `PROCESSING`, so a second batch assigned to the same branch on a later day would find it permanently locked. Not a Milestone 2 regression - the original in-memory `branchProcessingStatusState` Map had the identical one-way semantics (a process restart, not a real operational reset, was its only escape). Whether a branch's lock should ever clear for a new processing cycle is a business-workflow question, genuinely undecided, not an oversight.
- **Signed URL TTL (1 hour) and the business-domain 90-minute `TEMPORARY -> EXPIRED` proof-expiry window are two unrelated things that are not reconciled with each other** - neither is enforced against the other. Proof expiry enforcement itself remains unimplemented (carried forward, see "Correctness" section, `expiresAt` note).
- **No Storage DELETE policy exists for the `proof-of-payment` bucket** - consistent with proof deletion/expiry being unimplemented anywhere in the app today; will need revisiting together if expiry enforcement is ever built.
- **Storage RLS for `proof-of-payment` is role-based only, not branch-scoped** - unlike the table-level policies on `branch_processing_queue_items`/`proofs`, a Branch Officer's Storage access is not restricted to objects belonging to their own branch (parsing the object path inside a Storage policy was judged unwarranted complexity for a single-tenant internal app where the table-level RLS already scopes the metadata correctly). Worth reconsidering if REOS ever needs genuine per-branch Storage isolation.
- **Liquidity Management remains in-memory** - the last Phase 2 milestone, not attempted here. See "Persistence" section below.
- RESOLVED (2026-08-13, Production Readiness Phase 4): same RLS negative-path gap as Milestone 1 above - now also confirmed for `branch_processing_queue_items` specifically (both read and write, including a direct UPDATE attempt against another branch's queue item). Automated-regression-suite gap remains open (see "Testing" section below).

## Authentication & Authorization (new module, out-of-sprint, 2026-08-08)

Canonical spec: AUTHENTICATION.md. Items recorded there (Sections 10-11), tracked here for visibility:

- **`failedLoginAttempts`/`passwordChangedAt` are not tracked** - Supabase Auth's client-side API doesn't expose failed-attempt counts, and building that would mean a second, parallel auth-event log this phase doesn't add. `account_locked` (an explicit Admin action) is enforced; brute-force lockout is not.

## Correctness

- RESOLVED (Decision D-6, out-of-sprint, 2026-08-05): `BranchProcessingQueueItem` now carries `startedAt`, `completedAt`, `completedByUserId`, `returnedAt`, `returnedByUserId`, set by the `IN_PROGRESS` transition and by `completeBranchProcessingQueueItem`/`returnBranchProcessingQueueItem` (both gained an actor-id parameter). `proofDownloadService.buildProofDownloadBatchFromSharedBatch` no longer hardcodes `null` for these fields. `dashboardService.getAverageProcessingMinutes` now averages real `processingMinutes` values (computed by `reportingProjectionService`, per REPORTING_PROJECTION_LAYER.md Section 4.6's own design for this exact unblock) instead of returning a hardcoded `null`; `BranchPerformanceRow.processingSpeedMinutes` is now a real per-branch figure, so `getBranchHealth` is no longer forced to `YELLOW` for every branch. Purely additive in-memory state - no persistence. Verified by an 11-assertion functional smoke test. See CURRENT_SPRINT.md. **Not resolved by this fix, and separate scope**: no `PROCESSING_TIME`, `OFFICER_PERFORMANCE`, `RETURN_RATE` or `WORKLOAD` report *definitions* exist yet in `reportService.ts` - the underlying data now exists, but defining the reports (columns, filters, UI) is a distinct next milestone. Officer-attribution filtering (the User/Officer report filter) is likewise not yet wired to any report definition.
- **`SharedBatch.completedBeneficiaries` and `returnedBeneficiaries` are never incremented** (found Sprint 16 M4.2). Both are set to `0` at every creation site (`sharedBatchService.createSharedBatch`, `excelValidationService`, `BranchAssignmentPage`) and nothing anywhere increments them - Branch Processing tracks completion on its own queue items instead. Consequence: they read `0` even for a fully processed batch, and `reportService.mapSharedBatchToRow` maps them straight into the Shared Batches volume report's `completedCount` / `returnedCount` columns, so that report would show zero completed and zero returned work for a batch that was genuinely completed. `dashboardService` also filters on `returnedBeneficiaries > 0` to build its "Returned Batches" work-queue category, which can therefore never match. Not fixed - keeping these counters in step with the queue is a business-logic change in Shared Batch and Branch Processing, outside M4.2's read-only scope. The projection layer works around it correctly without hiding it: `BatchReportProjection` projects both the stale `SharedBatch` counters and the live queue-derived counts from `getBatchDownloadSummary`, under names that distinguish them.
- **Two transaction status vocabularies exist and one collapses the other** (found Sprint 16 architecture review). `BranchProcessingQueueStatus` is `ASSIGNED | IN_PROGRESS | COMPLETED | ON_HOLD | RETURNED`; `CreditToAccountTransactionStatus` is `PENDING | COMPLETED | RETURNED`. `proofDownloadService.toTransactionStatus` maps `ASSIGNED`, `IN_PROGRESS` and `ON_HOLD` all to `PENDING`, destroying the on-hold distinction. Any "Pending Work" or "On Hold Transactions" report must therefore project from `BranchProcessingQueueItem` directly. Recorded as a design constraint, not to be resolved by introducing a third status enum.
- RESOLVED (Sprint 15 M1.75): `branchProcessingQueueService.hydrateBranchProcessingQueue` was not idempotent - it ran on every mount of `BranchProcessingQueue.tsx` and unconditionally rebuilt that branch's queue from scratch (fresh `ASSIGNED` status, empty `proofs`, branch-level status reset to `PROCESSING`), silently discarding real completed work whenever a user navigated away and back. Pre-dated Sprint 14/15 (Sprint 13 code). Fixed by preserving existing queue items by their deterministic id and no longer resetting branch-level status on rehydration; only genuinely new assignment-beneficiary pairs get fresh items. Verified live against the exact reproduction that found it - see CURRENT_SPRINT.md, "M1.75".
- `proofOfPaymentService.markProofDownloaded` (sets an individual `ProofOfPayment.status` to `DOWNLOADED`) is never called anywhere, including by `downloadIndividualProof`/`downloadProofZip`. Wiring it in needs a write path back into `branchProcessingQueueService`'s queue-item state and an unstated product decision: does a ZIP download mark every included proof downloaded, or only individually-downloaded ones? Left as an open business decision, not assumed.
- Proof expiry is only enforced via the `status` field, never against `expiresAt`. Nothing automatically flags an expired proof as `EXPIRED` (no scheduler - BUSINESS_RULES.md puts one out of scope), so a proof past its 90-minute window but never explicitly marked can still appear downloadable.

- **Confirmed absence, not just unchecked (updated 2026-08-15, Production Readiness Phase 5): no automated, CI-integrated regression suite exists anywhere in this repository.** Every verification this project has ever run - Sprint 15 onward, through all five Production Readiness phases this session - has been a hand-written Playwright or direct-Supabase-API script (`.cjs`, prefixed `_`), executed once against the live dev server and real Supabase project, then deleted immediately after.
